3. What PitchProX is (plain words)

PitchProX is a website where sales teams make phone calls with an AI coach listening. While a salesperson talks to a customer, the AI shows live tips on screen (e.g. "they said it's too expensive → say this"). After the call, it gives a summary, a score and a recording.

Around that core it has: a lead list and CRM pipeline, sales scripts ("playbooks"), AI training, analytics, billing by call minutes, support tickets, email, and a compliance section for security audits (SOC 2).

The first users are real-estate agents — the lead types are things like "Expired Listings", "FSBO", "Probate".

What the app means for the backend
  • Token login (access + refresh tokens) for the app — the current cookie login only works in the browser.
  • Email OTP endpoints (send code, verify code) and push notifications (register the phone, send alerts).
  • The same API for website and app, with clear documentation so the app developer can use it.
  • Subscriptions inside an iPhone/Android app may have to go through Apple/Google payments, not just Stripe. Ask the client how the app should sell plans.

6. The big decision: where the backend lives

The spec (PROJECT_SPECIFICATION.md) and what we built in Phase 1 don't match. Pick one with the client:

A — Inside Next.js (what Phase 1 did)B — Separate server (what the spec says)
WhereAPI routes inside this same repo (/api/v1/...)A new project (e.g. Django or Node) on its own server, port 8000
DatabaseMySQL (CloudPanel docs use MySQL)PostgreSQL + Redis (spec)
LoginCookie today — must add token login for the appJWT tokens (website and mobile app)
Good forOne codebase, one deploy, keeps all Phase 1 workMobile app, heavy AI/background jobs, a team that knows Python
Phase 1 workKeep as-isLogic and tests carry over; code must be ported
Live AI callingStill needs a small separate service for the live audio/AI streamBuilt in (Django Channels / Socket.io)
My recommendation Since there is a mobile app, the API needs token login either way. If the client doesn't require Django/Python → keep A, add token login now, and add a small separate service for live calls later. If the client wants Django/Python or a separate backend → switch to B now, before more is built. Ask before starting Phase 2.
