# Deploying PitchProx on CloudPanel

> **Beginner step-by-step version:** [docs/deploy-guide.html](docs/deploy-guide.html) (open in a browser).

PitchProx is a **Next.js / Node.js** application with a **MySQL** database. In CloudPanel, create a **Node.js Site**. Do not select Python or Static HTML.

> **Release gate:** do not deploy this application as a public production site until `npm run lint` and `npm run build` pass in a clean environment and the dependency-security findings have been resolved. The current GitHub workflow intentionally blocks deployment when either check fails. A staging deployment is fine once the steps below are complete.

## What You Need

- A CloudPanel v2 server with a domain pointed at its public IP address
- Node.js 22 LTS selected in CloudPanel
- A new, production-only MySQL database and database user
- SSH access as the CloudPanel **site user** (not root)
- A private Git repository or another secure way to upload the application

CloudPanel creates a separate site user and stores that site's files below `/home/<site-user>/htdocs/<domain>/`. Its Node.js Site setting reverse-proxies web traffic to the App Port you select.

## 1. Create the Site in CloudPanel

1. In **Sites**, select **+ Add Site**.
2. Choose **Create a Node.js Site**.
3. Enter the real domain, such as `app.example.com`.
4. Select **Node.js 22 LTS**.
5. Set an unused App Port, for example **3005**. Keep this exact number for the `PORT` setting below.
6. Create the site. Note the generated site-user name.
7. In the site's SSL area, issue a Let's Encrypt certificate after DNS points to the server.

CloudPanel forwards NGINX traffic to this App Port. Do not expose port 3005 to the public internet; only HTTP/HTTPS (80/443) should be public.

## 2. Create a Separate Production Database

In CloudPanel's database area, create:

- Database: `pitchprox_prod`
- Database user: `pitchprox_app`
- A long, unique password generated by your password manager

Grant that user access only to `pitchprox_prod`. Do not reuse the local `pitchprox_dev` database, its local password, or any development data.

The current application creates its required tables automatically on first connection. For a hardened production setup, create/apply database migrations using a deployment account and give the runtime account only the minimum DML permissions afterwards.

## 3. Upload the Project and Install It

Log in using the CloudPanel site user, then go to the directory CloudPanel created (replace the placeholders):

```bash
ssh <site-user>@<server-ip>
cd /home/<site-user>/htdocs/<your-domain>
```

Upload or clone the repository into that directory. Do **not** upload `.env.local`, `node_modules`, `.git`, or an existing `.next` directory from a development computer.

Install every dependency needed to create the production build, then build:

```bash
npm ci
NODE_ENV=production npm run build
```

Do not use `npm ci --production` before the build: this project needs its development dependencies to run the build step.

## 4. Create the Server-Only Environment File

On the server, create `.env.local` in the project root. It is deliberately ignored by Git and must never be committed:

```dotenv
NODE_ENV=production
PORT=3005
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_DATABASE=pitchprox_prod
MYSQL_USER=pitchprox_app
MYSQL_PASSWORD=<long-unique-production-password>
```

Use the database host supplied by your provider if MySQL is remote. Restrict the file so only the site user can read it:

```bash
chmod 600 .env.local
```

Before starting the site, rotate any old server, database, or repository credentials that might have been present while the earlier malicious code was in the project.

## 5. Run Next.js with PM2

CloudPanel recommends PM2 for Node.js processes. As the site user:

```bash
npm install pm2@latest -g
cd /home/<site-user>/htdocs/<your-domain>
pm2 start npm --name pitchprox -- start
pm2 save
```

Verify it is online and inspect errors if it is not:

```bash
pm2 status
pm2 logs pitchprox --lines 100
curl -I http://127.0.0.1:3005/
```

Make PM2 survive reboots. CloudPanel's documented approach is to add the current Node/PM2 path and `pm2 resurrect` to the site user's crontab:

```bash
echo $PATH
crontab -e
```

Add these two lines, replacing the path with the output from `echo $PATH`:

```cron
PATH=<paste-the-output-of-echo-PATH-here>
@reboot pm2 resurrect &> /dev/null
```

## 6. Verify the Live Site

1. Open `https://<your-domain>` and confirm SSL is valid.
2. Create a fresh test account, sign in, update the profile, and sign out/in.
3. Create a lead and a CRM prospect, then check they remain after a refresh.
4. Check `pm2 logs pitchprox --lines 100` for database or application errors.
5. Confirm MySQL (3306) and the Node App Port (3005) are not reachable from the public internet.

## Updating the Site Manually

For each release, first run the checks in CI or locally, then on the server:

```bash
cd /home/<site-user>/htdocs/<your-domain>
# upload/pull the approved code here
npm ci
NODE_ENV=production npm run build
pm2 restart pitchprox --update-env
pm2 save
```

Always preserve the server's `.env.local` file. Take a database backup before schema changes or a release that changes data handling.

## GitHub Actions Note

This repository includes `.github/workflows/deploy.yml`, but it is not ready to be treated as a hands-off production deploy until the lint/build gate is green and the remote dependency-install step is explicitly handled. Its rsync transfer deliberately excludes environment files and `node_modules`; keep production secrets only on the server. Start with the manual process above, then update the workflow to run the same remote install/build/restart sequence or move to release directories for zero-downtime deployments.

# Client preview on Vercel (demo mode)

A preview link where the client chooses a role (Customer, Sales Rep, Super Admin, Admin Manager, Support, Auditor, New employee) and looks around with sample data. There is no sign-in screen: `/sign-in` and the portals send visitors to `/demo`. This is for showing the product only. Don't use it as the production site.

1. **Create a hosted MySQL database** (Aiven, TiDB Cloud, Railway, PlanetScale…). Note the host, port, database name, user and password.
2. **Load the sample data from your computer**, pointing at that database:
   ```bash
   MYSQL_HOST=… MYSQL_PORT=… MYSQL_DATABASE=… MYSQL_USER=… MYSQL_PASSWORD=… MYSQL_SSL=true npm run db:seed:demo
   ```
   The app creates its tables on the first connection. Running the command again adds nothing.
3. **Import the GitHub repo in Vercel** (New Project → pick the repo; keep the Next.js defaults).
4. **Add the environment variables** (Project → Settings → Environment Variables):

   | Name | Value |
   |---|---|
   | `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD` | from step 1 |
   | `MYSQL_SSL` | `true` |
   | `MYSQL_CONNECTION_LIMIT` | `3` |
   | `DEMO_MODE` | `true` |
   | `UPLOAD_DIR` | `/tmp/uploads`: uploads then work, but disappear after a while (fine for a demo) |

5. **Redeploy** (Deployments → ⋯ → Redeploy) so the variables apply, then share `https://<your-project>.vercel.app/demo`.

Notes
- Anyone with the link can open any role and change the sample data. To reset, empty the database and run step 2 again.
- If the database rejects the certificate (self-signed CA), also set `MYSQL_SSL_INSECURE=true`. It's acceptable for a demo; don't use it in production.
- The CloudPanel GitHub workflow is separate from Vercel. Its red ❌ on GitHub doesn't affect the preview.
